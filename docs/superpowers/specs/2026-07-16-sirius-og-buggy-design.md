# Sirius OG Buggy: дизайн ветки с 55 воспроизводимыми багами

## Цель

Создать ветку `sirius-og-buggy`, в которой одновременно воспроизводятся все 55 задач из `sympy_og_tickets.csv`. Каждая задача должна быть представлена реальной регрессией в коде SymPy и одной или несколькими проверками, основанными на официальной записи SWE-bench.

## Границы работы

- Работа ведётся только в новой ветке `sirius-og-buggy` и worktree `sympy-sirius-light/og-buggy`. Внутри worktree используется каталог `bugs_cards/`, аналогично ветке `sirius-light-buggy`.
- Ветки `sirius-light-buggy`, `sirius-light-golden` и ручное изменение `README.md` в master-worktree не меняются.
- `sympy_og_tickets.csv` в `sirius-swebench-light` остаётся неизменным источником метаданных.
- Полные записи SWE-bench из `sympy_og_tickets_full.jsonl` используются как строительный источник, но не публикуются в buggy-ветке: они содержат готовые исправления и создают утечку ответа для учебного агента.
- Новая golden-ветка в этом цикле не создаётся: подтверждённый результат ограничен веткой `sirius-og-buggy`.

## Основа ветки

Ветка создаётся от зафиксированного `master` (`bd337318`). Это сохраняет актуальный снимок SymPy и учебную документацию, не захватывая незакоммиченные пользовательские изменения из master-worktree.

## Данные и учебные файлы

В `bugs_cards/` добавляются:

- `sympy_og_tickets.csv` — неизменная копия исходного CSV с 55 строками;
- `sympy_og_tickets_input.csv` — вход для агента с пятью колонками: `instance_id`, `title`, `ticket_description`, `expected_fail_to_pass_tests`, `test_files`;
- `template.md` — короткий шаблон карточки задачи, если его ещё нет в выбранной основе.

Golden patches и `test_patch` в `bugs_cards/` не помещаются.

## Воспроизведение багов

Для каждой записи выполняется один и тот же цикл:

1. Из официальных `test_patch` и `FAIL_TO_PASS` выделяется минимальная проверка поведения.
2. Проверка адаптируется к актуальному API SymPy без изменения её смысла.
3. На исходном снимке проверка должна проходить, подтверждая наличие исправления.
4. Официальный `patch` обращается. Если он не применяется к современной версии, прежнее ошибочное поведение восстанавливается вручную только в перечисленных `patch_files`.
5. После изменения проверка должна падать по причине соответствующего бага, а не из-за импорта, синтаксиса или окружения.

Все проверки размещаются в `sirius_tests/test_sympy_og_bugs.py`. Каждый тестовый случай должен быть однозначно связан с `instance_id`. Если одна официальная задача содержит несколько независимых `FAIL_TO_PASS`, для неё можно сохранить несколько отдельных проверок. Общее количество проверок заранее не фиксируется.

## Конфликты между регрессиями

По текущему CSV задачи не пересекаются по конкретным `patch_files`, поэтому изменения в коде можно вносить независимо. Пересечения есть в пяти тестовых файлах; адаптированные проверки из них объединяются так, чтобы сохранялся смысл каждой официальной задачи. После каждого изменения запускаются проверки текущей задачи, а после каждой группы из 5–10 задач — весь учебный файл.

Если официальную семантику невозможно перенести на текущий снимок без разрушения другой задачи, работа останавливается на конкретном `instance_id` с сохранением уже подтверждённых результатов и описанием конфликта.

## Скрипты

- `scripts/setup_sirius.sh` создаёт общую соседнюю `.venv` и устанавливает текущий репозиторий, `pytest` и `hypothesis`.
- `scripts/run_sirius_tests.sh` запускает только `sirius_tests/test_sympy_og_bugs.py`.

Полный test suite SymPy не запускается.

## Критерии проверки

Готовая ветка должна удовлетворять всем условиям:

- в датасете и агентском CSV ровно 55 уникальных `instance_id`;
- учебный файл покрывает все 55 `instance_id` хотя бы одной проверкой на задачу;
- одна задача может иметь несколько проверок, поэтому их итоговое количество может быть больше 55;
- на неизменённой основе все регрессионные проверки проходят;
- в `sirius-og-buggy` все регрессионные проверки падают по ожидаемой причине;
- импорты и сборка тестов проходят без ошибок;
- существующие light-ветки и master-worktree сохраняют исходные статусы;
- в итоговом отчёте приведена таблица `instance_id → тест → изменённые файлы → причина падения`.

## Обработка ошибок

- Несовпадение `instance_id` или `base_commit` между CSV и официальной записью считается ошибкой входных данных.
- Пустые `patch`, `test_patch`, `FAIL_TO_PASS` или `PASS_TO_PASS` запрещены.
- Падение из-за отсутствующей зависимости сначала устраняется в setup-скрипте; такое падение не засчитывается как воспроизведённый баг.
- Любое изменение вне новой ветки или её worktree считается нарушением границ работы.
